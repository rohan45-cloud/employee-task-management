# Employee & Task Management System

MERN implementation for the Roots Media Marketing MERN Stack Developer Intern assignment.

## Stack
- React + Vite, React Router, Axios, Lucide React, React Toastify
- Node.js, Express, Mongoose
- MongoDB Atlas (recommended; transactions require a replica set)

## Run locally
1. Install Node.js 18+ and MongoDB Atlas.
2. Backend:
   ```bash
   cd backend
   cp .env.example .env
   # Set MONGO_URI and CLIENT_URL in .env
   npm install
   npm run dev
   ```
3. Frontend (new terminal):
   ```bash
   cd frontend
   cp .env.example .env
   npm install
   npm run dev
   ```
4. Open http://localhost:5173

## Environment
Backend `.env`:
- `PORT`: API port (default 5000)
- `MONGO_URI`: MongoDB connection string
- `CLIENT_URL`: frontend origin(s) allowed by CORS, without a trailing slash. Multiple origins can be comma separated.

Frontend `.env`:
- `VITE_API_URL`: backend base URL, e.g. `http://localhost:5000/api`

Never commit real `.env` files or credentials.

## API overview
### Employees
- `GET /api/employees?page=1&limit=10&search=&department=&status=&sortBy=fullName&sortOrder=asc`
- `POST /api/employees`
- `GET /api/employees/:id`
- `PUT /api/employees/:id`
- `DELETE /api/employees/:id`

### Tasks
- `GET /api/tasks?page=1&limit=10&search=&department=&priority=&status=&dueFrom=&dueTo=&sortBy=createdAt&sortOrder=desc`
- `POST /api/tasks`
- `GET /api/tasks/:id`
- `PUT /api/tasks/:id` (status is deliberately not editable here)
- `DELETE /api/tasks/:id` (only non-terminal tasks can be deleted)
- `PUT /api/tasks/:id/status`
- `GET /api/tasks/export/csv` (exports every matching task, ignoring pagination)

### Dashboard
- `GET /api/dashboard`

All list APIs return `{ success, data, pagination }`. Errors use `{ success:false, message }`.

## Data model and relationship
An Employee has a unique employeeId and normalized unique email. A Task stores `assignedEmployee` as an ObjectId reference and also stores an `employeeSnapshot` (employee ID, name, email, department). The snapshot preserves meaningful employee information if the employee is later deleted. The task's department is stored on the task as required by the assignment.

## Business rules and design decisions
1. **Status transitions:** enforced in the backend status endpoint and service, not the normal task update endpoint. Only Todo → In Progress, Todo → Cancelled, In Progress → Completed, and In Progress → Cancelled are allowed. Completed and Cancelled tasks are immutable.
2. **Completed Date:** generated by the backend at the moment a task transitions to Completed. A client must never be trusted to provide this timestamp.
3. **Employee assignment:** task create/update checks employee status. Inactive is always rejected. On Leave is rejected only when task Start Date is inclusively between leaveStart and leaveEnd.
4. **Capacity:** at most three Todo/In Progress tasks per employee. A conditional atomic employee counter reservation (`activeTaskCount < 3`) prevents two simultaneous requests from both claiming the final slot. The counter is updated on task status and assignment changes. The employee counter is a denormalized concurrency guard; task create/update/status/delete operations maintain it.
5. **Filtering and pagination:** performed in MongoDB on the server to avoid downloading all records, reduce client work, and return consistent page metadata. Search and filters can be combined.
6. **URL state:** list search, filters, sort and page are query parameters so refresh, browser navigation and copied links reproduce the same view.
7. **Concurrent fourth assignment:** without an atomic guard, two requests can both read a count of two and each create a third task, or exceed capacity due to stale reads. The conditional atomic update serializes reservations; one request gets the final slot and the other receives HTTP 400. For deployments with multiple related writes, MongoDB transactions are recommended and the configured MongoDB deployment should support them.
8. **Employee deletion:** blocked when active tasks exist. Historical/terminal tasks retain employeeSnapshot; their populated employee reference may become null.
9. **Overdue:** computed using the server's current date and `dueDate < today`, excluding Completed and Cancelled, and returned for list, detail, dashboard and CSV.
10. **Assumptions:** task department is selected explicitly and may differ from employee department; employee skills are an array of strings; employee phone is stored as a string; task status can only change through the dedicated status endpoint.

## Deployment
- **Frontend (Vercel):** https://employee-task-management-dar2.vercel.app
- **Backend (Render):** https://employee-task-management-s7z1.onrender.com
- **API base URL:** https://employee-task-management-s7z1.onrender.com/api

### Backend (Render)
Root Directory `backend`, Build `npm install`, Start `npm start`.
Environment variables: `MONGO_URI`, `CLIENT_URL` (the Vercel frontend URL, without a trailing slash), `PORT` (optional).

### Frontend (Vercel)
Root Directory `frontend`, Build `npm run build`, Output `dist`.
Environment variable: `VITE_API_URL=https://employee-task-management-s7z1.onrender.com/api`.
`vercel.json` contains a rewrite so React Router routes work on refresh.

> Note: the backend runs on Render's free plan, so the first request after inactivity can take 30-60 seconds.
